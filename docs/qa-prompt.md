# TwoFlip 화면 QA · UI/UX 제안

> **지금은 [정기 QA 틀(docs/qa-regular.md)](qa-regular.md)을 쓴다**(12차 · 10-15부터). 이 문서는 10-14 1차 QA 기준 기록이다.

> 다른 Claude 세션(브라우저 사용)이나 사람에게 이 문서를 그대로 넘긴다. 테스트 계정 비밀번호는 여기 적지 않는다 — 재영이 따로 전달한다.
> 화면이 바뀌면 이 문서의 체크리스트도 같이 고친다. (작성 2026-10-14 · 관리자 로그인 화면 PR #8 기준)

## 너의 역할

TwoFlip 의 웹 화면을 **직접 써 보고** 두 가지를 낸다.

1. **버그** — 동작이 틀린 것(재현 절차와 함께)
2. **UI/UX 제안** — 동작은 하지만 고객·운영자가 헷갈리거나, 느리거나, 불안하거나, 그만두게 되는 지점과 그 개선안

코드를 고치지 않는다. 제안은 근거(어느 화면에서 무엇을 하다가 어디서 막혔는지)와 함께 낸다. 「더 예쁘게」 같은 취향 의견보다 **사용자가 목표를 이루는 데 걸리는 것**을 우선한다.

## 서비스 이해(제안 전에 읽기)

- **무엇:** 고객이 KREAM 상품 링크를 남기면, 운영자가 공식몰·근처 오프라인 매장·해외에서 그 상품·사이즈 재고를 직접 확인해 확보하고, 고객에게 연락해 KREAM 대신 넘겨주는 구매대행. 사업명 Threefold(쓰리폴드), 3명이 공동 운영.
- **흐름:** 신청 → (운영자) 탐색 중 → 확보 → 연락 완료 → 결제 완료 → 완료 / 취소
- **지금 단계:** 소규모 시작 · 확인용 임시 운영. 관리자 화면·로그인은 임시다. 결제·배송·고객 계정은 아직 없다.
- **정해지지 않은 것(제안은 해도 되지만 「정해졌다」고 가정하지 않는다):** 가격·수수료 기준, 확보 실패 시 처리, 결제 방식, 고객 연락 수단, 수익 배분, 권한 체계.
- **원칙:** 확인하지 못한 값은 지어내지 않고 「미확인」으로 보인다 · 예상 수익을 확정처럼 보이지 않는다(「KREAM 대비」는 수수료·배송비 전) · 일정 마진·수익을 보장하는 표현을 쓰지 않는다. 제안도 이 원칙을 깨지 않아야 한다.

## 반드시 지킬 것

1. **실제 서버에 넣는 테스트 신청은 이름을 `[QA] 이름` 으로, 휴대폰은 `010-0000-0000` 으로**만 한다. 실제 고객 신청(이름에 `[QA]` 가 없는 것)은 **상태·재고·담당자를 바꾸거나 지우지 않는다** — 보기만 한다.
2. QA 가 끝나면 관리자 화면에서 `[QA]` 신청을 전부 지운다(06 신청자 → 「이 신청 삭제」).
3. 요청 제한이 있다: 같은 IP 에서 신청 10분 5번, 관리자 로그인 시도 10분 10번. 넘으면 「너무 잦습니다」가 나오는 게 **정상**이다(버그 아님). 일부러 많이 두드리지 않는다.
4. 아래 「알려진 동작」은 버그로 올리지 않는다(UX 제안으로는 올려도 된다).
5. 비밀번호·접속 키·실제 고객 전화번호를 보고서·스크린샷에 남기지 않는다.

## 알려진 동작(버그 아님)

- 실제 신청 화면에서 KREAM 링크를 넣으면 「지금은 KREAM 정보를 불러올 수 없습니다. 신청은 그대로 할 수 있습니다」가 나온다 — 서버 IP 를 KREAM 이 막고 있다. 신청은 저장되고, 나중에 사무실 PC 가 KREAM 정보를 채운다(`twoflip_backend` 의 `tools/kream-fill.php`).
- 테스트 모드에서는 「테스트 모드에서는 KREAM 상품 정보를 불러오지 않습니다」.
- 관리자 화면의 공식몰·지도·해외 링크는 **검색 링크**다(재고를 자동 조회하지 않음). 재고 확인 기록은 전부 「수동」.
- 「KREAM 대비」는 KREAM 수수료·배송비 전 금액이다.
- 신청 KREAM 정보가 없는 카드는 「상품 정보 없음」 + 01 칸에 브랜드·모델번호 직접 입력 칸이 보인다.

## 사용자와 시나리오 — 이 사람이 되어 써 본다

### 고객 「민지」 — 신청 화면
- 20대, 휴대폰으로 KREAM 앱을 보다가 사고 싶은 신발(270)이 너무 비싸서 들어왔다. KREAM 앱의 「공유」로 링크를 복사했다.
- 궁금한 것: 여기가 믿을 만한가? 얼마에 살 수 있나? 언제 연락이 오나? 내 번호로 뭘 하나? 안 구해지면?
- 목표: **1분 안에, 불안하지 않게** 신청을 끝낸다.
- 해 볼 것: 375px 에서 링크 붙여넣기 → 사이즈 고르기(미리보기가 안 나오는 상황 포함) → 연락처 → 신청 → 접수 화면에서 「이제 뭘 기다리면 되는지」 알 수 있는지.

### 운영자 「재영」 — 관리자 화면(사무실 PC)
- 아침에 밤사이 들어온 신청을 정리한다. 3명이 나눠 맡는다.
- 목표: **오늘 확인할 신청을 빨리 찾고**, 공식몰·매장·해외를 확인해 기록하고, 확보 가능한 건을 골라 담당자를 정한다.
- 해 볼 것: 로그인 → 「재고 확인 필요」 찾기 → 한 건 열어 02~04 링크로 확인 → 05 에 2~3곳 기록 → 상태·담당자 변경 → 다음 건으로.

### 운영자 「민수」 — 관리자 화면(매장에서 휴대폰)
- 오프라인 매장에 서서 재고를 직원에게 물어보고 바로 기록한다. 한 손, 375px, 이동 중.
- 목표: **그 자리에서 30초 안에** 「강남점 · 270 · 재고 있음 · 가격」을 남긴다.
- 해 볼 것: 휴대폰 로그인(로그인 유지) → 해당 신청 찾기 → 05 재고 기록 → 품절이면 바로 바꾸기.

## UI/UX 볼 것(관점)

각 화면을 아래 관점으로 본다. 해당 없는 건 건너뛴다.

| 관점 | 질문 |
|---|---|
| 목표 달성 | 위 시나리오를 막힘 없이 끝낼 수 있나? 몇 번 누르고 몇 초 걸리나? 어디서 멈칫했나? |
| 이해 | 처음 보는 사람이 문구·버튼·배지(「재고 미확인」「오래됨」「KREAM 대비」 등)의 뜻을 바로 아나? |
| 신뢰(고객) | 개인정보·가격·진행 과정에 대해 불안을 줄이는 정보가 있나? 무엇이 빠져서 그만두고 싶어지나? |
| 오류 대처 | 실패했을 때(미리보기 안 됨, 형식 틀림, 요청 제한, 로그인 만료) 다음에 뭘 하면 되는지 아나? 입력한 게 날아가지 않나? |
| 정보 우선순위 | 가장 자주 보는 정보(재고 요약, 최저가, 상태, 담당)가 먼저 보이나? 한 카드에 너무 많지 않나? |
| 반복 작업 효율(운영자) | 여러 건을 연속으로 처리할 때 불필요한 스크롤·클릭·다시 입력이 있나? 단축·일괄 처리가 필요한가? |
| 모바일 | 375px 에서 손가락으로 누르기 쉬운가(버튼 크기·간격)? 표·입력 칸이 쓸 만한가? 키보드가 칸을 가리지 않나? |
| 일관성 | 같은 뜻에 같은 말·색·위치를 쓰나? 신청 화면과 관리자 화면 말투가 맞나? |
| 접근성 | 키보드만으로 되나? 포커스가 보이나? 색만으로 구분하지 않나? 다크 모드 대비가 충분한가? |
| 피드백 | 저장·변경 후 「됐다」는 신호가 분명한가? 느린 동작에 진행 표시가 있나? |

## 보고 형식

### 1) 버그 — 하나마다

```
[B-번호] [심각도] 높음(데이터 손실·노출, 신청 불가) / 중간(기능 오동작) / 낮음(표시·문구)
화면: 신청 / 테스트 모드 / 관리자-로그인 / 관리자-목록 / 관리자-카드(01~06)
환경: 브라우저 · 폭(1280/375) · 라이트/다크
재현: 1) … 2) … 3) …
기대: …
실제: …
첨부: 스크린샷(비밀번호·전화번호 원문은 가리기)
```

### 2) UI/UX 제안 — 하나마다

